## Wave & coordination model (UAT-driven, collision-free)

**Core principle — the UAT drives the refactoring.** Pillar A (generated-CRUD conversion, bootstrap-table generation, router split) is *behavior-preserving* plumbing: it must change nothing observable. So the success criterion for every such change is **"the characterization UAT stayed green,"** not reviewer judgment. The behavioral safety net (Pillar A0) is therefore built **first** and *gates* the refactor.

**The tight loop (the whole point):** pick any Pillar A item → **run that domain's characterization suite (baseline green)** → refactor → **run it again immediately** → green = behavior preserved, ship it; red = the refactor broke something, revert. This requires the characterization suite to be **on-demand and per-domain** (e.g. `bin/uat-characterize.ps1 <domain>`), runnable in seconds against staging — *not* only in the deploy gate. Refactor → test-immediately is the design target.

**Coverage-gates-refactor rule (hard):** **a domain may not be refactored until Pillar A0 has characterized it** — happy path, error/edge paths, **and tenant-isolation assertions** ("a user in org A cannot read/write org B's data" for every endpoint). Uncharacterized domains are off-limits; coverage is the unlock. This protects the property that the raw-SQL→CRUD conversion most risks regressing (a dropped `org_id` filter = cross-tenant PHI leak), which a string-match test would never catch.

- **Wave 0 — Safety net + ratchet (the driver):** **A0 characterization UAT** (Agent4, per-domain, on-demand) + **A1 no-raw-SQL ratchet** land first. A0 is the pacing item — each domain it characterizes becomes *unlocked* for refactoring. B1–B3 (ungit `.class`, provenance, fatal-compile) + A6 (migrations) land alongside.
- **Wave 1 — Refactor behind the net + per-lane core.** A2 (router split) + A4/A5 (CRUD conversion) proceed **domain-by-domain, gated on green A0 coverage for that domain**, via the tight loop above. In parallel, agents build production-core features in already-characterized areas.
- **Wave 2 — Integration & maturity.** Cross-lane wiring (executors, real adapters, end-to-end).
- **Wave 3 — Hardening, scale, certification evidence.**

**Order of operations per domain:** characterize (A0) → unlock → refactor (A2/A4/A5) with the test running before *and* after each step → next domain.

**Hot-file rule:** the router (`server/ClaimsProcessingRouter.script`) stays serialized through `enqueue-deploy.ps1` until A2 (router split) completes; after that, domain modules are independently owned. Generated `data/*` and `ClaimsProcessingViews.xml` changes coordinate through Agent1 (CRUD lead) to avoid regen races.
