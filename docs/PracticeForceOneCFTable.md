### §9-DOE — Diagnostic Order Engine (founder architectural directive 2026-07-18) 🏛️

**Directive (founder 2026-07-18):** *"Rather than implementing those as separate features, build a single Diagnostic Order Engine."* The OR/RF/LB findings below must NOT be built as one-off screens (`orders.html`, `referrals.html`, a results queue, an order-sets module, …). They are **outputs of one durable engine** so PracticeForceOne scales from today's mock integrations to production laboratory/registry connectivity **without redesigning the workflow**.

**One engine, four order kinds, one lifecycle, pluggable transport:**

- **Order kinds (one model, discriminated):** `lab` · `imaging` · `procedure` · `referral`. Today `diagnostic_orders` (lab/imaging, ECW-OR-1, live 1791) and `referrals` (ECW-RF-1, live 1791) are separate tables — the engine unifies them behind a shared **order lifecycle + shared work-queue + shared transport seam** (keep the physical tables if convenient; unify the *contract & lifecycle*, don't force a risky migration).
- **Shared lifecycle:** `Draft → Signed → Transmitted → Acknowledged → Result/Consult-received → Closed` (+ `Failed`/rework lane for 278/HL7 rejections). Every kind burns down the same status ladder → one work-queue console serves all four.
- **Pluggable transport (the durable seam — the whole point):** an `OrderTransport` interface with `transmit(order)` / `poll(ack)` / `ingestResult(payload)`. **`MockTransport` today** (writes to `edi-queue`/logs, simulates ack+result); **`Fhir R4 ServiceRequest`/`Hl7v2 ORM/ORU` and `278` adapters later** — swap the adapter, workflow unchanged. No UI or workflow code calls a vendor directly; everything goes through the seam.
- **Work-queue console = a CF grid, not a bespoke page:** Outstanding/To-review/Reviewed/Future/Failed tabs (ECW-LB-2/RF-3) ride the **reusable configurable-grid capabilities** (sortable ✅ + CSV export ✅ live 1793; column-filters + row-actions next) — so the engine's queues come nearly free as the grid framework deepens. This is the leverage tie: *build the grid framework once, every order queue inherits it.*
- **Order sets (ECW-OR-3, theme 8):** named dx-based bundles that emit N engine orders in one action (compose, don't special-case).
- **Order-to-billing glue (ECW-OR-2):** dx→CPT association at sign time so orders arrive billable (+ ABN artifact) — a lifecycle hook, not a separate feature.
- **Pre-auth rules (ECW-RF-9, theme 2):** payer×procedure rules auto-spawn a `referral`-kind order into the same queue (K-autopilot tie).

**Findings this engine subsumes** (see [ReferralsOrdersLabs matrix](<PracticeForceOneECWMatrixReferralsOrdersLabs.md>)): ECW-OR-1/2/3, ECW-RF-1..10, ECW-LB-1/2/3 (16 findings) + themes 2, 8, 23. Today: 🟢 OR-1, RF-1 live; the rest become **engine slices**, not new screens.

**Build order (proposed):** ① factor the shared lifecycle + `OrderTransport` seam over the existing `diagnostic_orders`/`referrals` routes (MockTransport) → ② one unified work-queue console on the reusable grid (row-actions + filters) → ③ results ingest lane (ECW-LB-1/2 Open→Reviewed + portal-publish control) → ④ order sets + dx→CPT/pre-auth hooks → ⑤ FHIR/HL7/278 adapters when the clearinghouse/lab interfaces activate. Each slice = full-stack CF (table/lifecycle → routes → definition → CF-n gate scenario). **Status: ☐ architectural goal accepted, not started (foundation OR-1/RF-1 live).**
