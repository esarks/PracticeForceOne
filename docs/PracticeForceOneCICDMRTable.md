## Working rules (read before taking a row)

1. **Scope:** the deploy *mechanics* — `cloudbuild.yaml`, `docker/Dockerfile`, `bin/` orchestration scripts, GCP trigger/IAM config, and the `pipeline/` area for the toolchain image. Application code is out of scope (a row that needs an app change must say so explicitly).
2. **Neither lane may break the other mid-MR.** The PC path (`ci-deploy.ps1`) and the cloud path (`pipeline/cloudbuild-deploy.yaml`) coexist until the item-7 reconciliation decision; changes to shared surfaces (the Cloud Run service's traffic model, the GCS lock/counter, env-var sets) must be posted to AGENTS.md before landing.
3. **Hot files (serialize via AGENTS.md claim):** `cloudbuild.yaml`, `pipeline/cloudbuild-deploy.yaml`, `docker/Dockerfile`, `bin/release-preflight.ps1`. One owner at a time.
4. **Evidence bar:** a row is Done only with runtime proof — a green pipeline run ID, a class-equivalence diff transcript, or a rehearsed procedure log. "The YAML looks right" is not proof.
5. **The class-equivalence gate (C1.3) is this MR's gate zero:** the 07-04 SEV1 proved the stale-class leak ships real outages. No cutover completion until the compile-data fix lands and the negative test is green.
6. **Identity rule:** no personal account in any new path — the pipeline runs as the dedicated deploy service account (C2.1). Founder-gated actions are marked **⛔founder**.
7. Coordination: AGENTS.md for claims and hand-offs; cutover steps require an explicit ALL-AGENTS notice + ack window.

### The problem being solved

Deploying PracticeForceOne originally required one specific Windows laptop: a chain of PowerShell scripts regenerated and recompiled the JAC data layer and router, gates ran a 140+-scenario characterization suite, and only the final stretch (Docker build, push, Cloud Run deploy) ran in Google Cloud Build — with the image **copying locally compiled classes from the laptop's working tree**. ## Retrospective — durable engineering lessons (2026-07-07 closeout, AgentCICD)

*Written at retirement. These are the lessons that transfer to any future platform work, not project history (the progress log above holds that).*

1. **The biggest architectural risk was invisible packaging, not code.** Shipping ANY pre-built artifact verbatim (`COPY classes/com` of a committed/working tree) means a stale or corrupt class ships silently and detonates at runtime — SEV1-1651 (all creates down) was exactly this, predicted by the negative test 5 days earlier. *Durable rule: every shipped artifact is compiled from source in-pipeline, and the proof is a **planted-fault negative test kept in the pipeline forever** — an equivalence diff only proves the day it ran.*
2. **Gate-green is not promote-safe: promotion needs content monotonicity.** Build 1672 promoted an older tree over a newer one because "passed the gate" was the only criterion — build *numbers* were monotonic, content was not. *Durable rule: promote must verify the serving commit is an ancestor of the candidate (`git merge-base --is-ancestor`).*
3. **Floating image tags leak un-gated bits.** An image pushed before its gate + anything resolving `:latest` = gate-FAILED content servable (happened 07-05). *Durable rule: the only floating tag is one applied AT promote (`:blessed`); redeploy paths pin digests.*
4. **Provenance is an incident-response asset, not metadata.** `/api/health` naming commit + contentHash turned three incidents (0%-traffic "DEPLOY COMPLETE", the 1672 rollback, stale-content reports) from mysteries into minutes-long diagnoses. The `gitCommit: unknown` era proved the negative. *Durable rule: no deploy path ships unstamped; the stamp must survive `builds submit`'s `.git` exclusion (pass it in).*
5. **Shared-resource ceilings masquerade as application regressions.** db-f1-micro's ~25 connection slots made gate failures look like cargo bugs (`f0522663` — cargo exonerated). *Durable rule: cap candidate scale (`--max-instances 2`), and when a gate fails with HTTP 0/503 clusters, check the shared ceiling before blaming the diff.*
6. **Two deploy lanes survive only on shared primitives.** The GCS build counter and cross-path lock kept dual-lane sane; every surface NOT shared broke — the cloud lane's promote-by-name silently stranded PC deploys at 0% traffic while they printed DEPLOY COMPLETE. *Durable rule: lanes must share the counter, the lock, AND the traffic model — or one lane must die (item 7).*
7. **Diagnostics must survive the failure.** javac's `[removal]` warning flood hid every real error past the console window; temp-source cleanup destroyed the evidence; three phase0 runs failed "invisibly." *Durable rule: on failure, persist the complete tool output to a file and keep the intermediate artifacts — truncated consoles are for humans watching, not for forensics.*
8. **Decisions that proved correct:** safe-canary (deploy no-traffic → full 199-scenario gate → promote) — repeatedly held bad builds off traffic; the founder's OneDrive-stays call — the hermetic pipeline made folder location irrelevant while keeping his crash-recovery path (OneDrive remained a *local build* hazard — locks, stale reads — which the cloud lane structurally sidesteps); vendoring the out-of-repo jac23 toolchain; JAC running unmodified on Linux (the biggest positive surprise — the "long pole" wasn't).
9. **Recommendation for what remains:** land the GitHub push trigger (item 5) — it structurally fixes provenance (real `.git`), serializes deploys, and removes the "who submits the cadence" ambiguity that cost a day of forensics; wire failure alerts (item 6) — every silent RED was found by a human asking; then execute the founder's deployment-model decision (Option A cloud-only recommended) and decommission the legacy queue (item 8).
