## §8 — Founder-requested: patient identity verification when phone/email is absent *(2026-06-23)*

**Founder ask:** *"account for if a patient doesn't have a phone or email — how can we validate them? And if all there is is last-4 of social, that's not good enough either."*

**M7-90 — Alternate patient identity proofing (no phone/email; SSN-4 insufficient).** Today portal verification leans on **email confirmation codes** (`PortalAuthRegisterRoutes`) + optional MFA — which **fails entirely for a patient with no phone or email**, and **last-4-SSN is a shared/known secret, not proof.** We need stronger, channel-independent proofing with assurance tiers. Status: **⏩ pushed to [MR9](<PracticeForceOneMR9Table.md>) → M9-8** — needs founder/product + compliance sign-off (identity proofing has HIPAA/state-law implications). Owner: TBD.

### ⭐ Founder's leading approach (2026-06-23): **DOB + a clinic-issued special PIN**
Verify the no-contact-info patient with **date of birth + a special PIN the clinic issues** (handed at a visit after an ID check, or mailed to the address on file). This is sound because it pairs a **corroborating identity factor** (DOB must match the record) with a **secret the clinic controls** (the PIN) — i.e., staff-mediated trust + an out-of-band code (recommendations #1 + #3 + #2 combined). **Guardrails that make it safe (DOB alone is low-entropy/semi-public, so the PIN carries the security):**
- **Clinic-issued, not patient-chosen** — generated server-side (≈6–8 chars, random), so it isn't a guessable/reused secret.
- **Single-use, short expiry** — it's an **activation** code: DOB + PIN → the patient then sets their own password. Not a recurring login factor.
- **Out-of-band delivery** — printed/handed at the front desk (strongest, with photo-ID check) or mailed to the on-file address; never shown in the same web session that's claiming the identity.
- **Rate-limit + lockout** — reuse the existing **verification-attempts lockout** + **account lockout (N1, live)** so DOB+PIN can't be brute-forced; near-misses route to staff review.
- **Tier the access** to how it was issued — a mailed PIN ⇒ standard access; an in-person ID-checked PIN ⇒ full access (recommendation #4).
- **Audit** which staff issued the PIN + when it was redeemed (recommendation #6 / M7-72).

### Recommendations (prioritized; the clinic itself is the strongest "trusted referee")
1. **In-person, staff-mediated activation (gold standard fallback).** When remote proofing is impossible, front-desk staff verify a **government photo ID** at a visit and then activate portal access by issuing a **one-time activation code** the patient redeems to set a password. This is the most defensible path for the no-contact-info patient and should be the **primary** answer.
2. **Multi-point knowledge verification on clinic-held PHI — never a single weak factor.** Instead of SSN-4 alone, require an **N-of-M match** across data the clinic already holds and an impostor is unlikely to have *together*: full legal name + DOB + address on file + **a recent appointment date/provider** + insurance member ID + MRN. (This is KBV on the clinic's own records — *not* credit-bureau KBA.) SSN-4 may be **one** corroborating field, never the deciding one.
3. **Out-of-band code via a channel the clinic controls.** No email/phone → mail a **one-time PIN to the address on file** (a recognized proofing method) or hand a printed activation code at a visit; the patient redeems it. Time-boxed, single-use, rate-limited.
4. **Tier access to the assurance level (NIST 800-63 IAL/AAL framing).** A weakly-verified account (KBV-only) gets **limited access** (e.g., view upcoming appointments) and **must** step up to in-person/mailed-PIN proofing before full PHI/records or any financial/clinical action. Don't expose full PHI on a weak factor.
5. **Verified proxy / guardian path.** For patients who genuinely can't self-verify (minors, elderly, unhoused), support a **consented proxy/guardian** (or alternate trusted contact) who is themselves verified and receives the activation code, with the relationship + consent on record.
6. **Document & audit the proofing method per account.** Record **how** each patient was verified (in-person ID / mailed PIN / KBV N-of-M), by whom, and when — for HIPAA audit + dispute resolution. (Ties to **M7-72** audit-trail reliability.)
7. **Anti-impostor controls (mostly already present).** Reuse the **account lockout** (N1, live) + the **verification-attempts lockout** (`validate-verification-attempts-lockout.ps1`); on a near-miss KBV, **route to staff review** rather than auto-allow or auto-deny.
8. **Make phone/email optional, proofing path required.** Registration shouldn't *require* contact info, but absent it must route the patient into one of the stronger paths above (and prompt to add a contact method later for recovery/MFA).

**Suggested DoD:** (a) a documented proofing-tier policy (founder + compliance signed); (b) a staff "verify & activate" flow that records ID-check + issues an activation code; (c) KBV N-of-M on clinic data with staff-review on near-miss; (d) the proofing method/tier stored + audited per account; (e) tiered portal access gated on the recorded assurance level. Most is back-end + portal/staff UI; no vendor required (an optional future upgrade is a real IAL-2 identity-proofing vendor).
